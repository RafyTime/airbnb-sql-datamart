# **Portfolio Project — Phase 3**

## **Final Abstract**

This project designed and implemented a relational datamart for an Airbnb-style accommodation booking platform. The original problem was to model the database backbone for a lean marketplace where guests can discover and book short-term stays, hosts can publish and manage listings, and admins can supervise platform activity. The scope was intentionally kept realistic for an MVP. It included identity and roles, listings, locations, availability, bookings, pricing, payments, payouts, cancellation policies, wishlists, reviews, messaging, notifications, and referrals, while leaving more advanced areas such as disputes, advanced pricing, and KYC outside the main implementation.

The first phase established the conceptual foundation for the project. Several important assumptions shaped the model from the beginning. A single user could act as a guest, host, or admin through a role mapping instead of separate user tables. Locations would be stored hierarchically to reduce repeated geographic text. Bookings would enforce valid date ranges, and the system would separate guest payments from host payouts. Reviews would be tied to real bookings, ratings would be constrained, and booking totals would be stored while still preserving itemized booking fees for transparency. These decisions made the ER model more detailed, but they also made the later SQL implementation more stable.

The ER model was derived from the main business workflows of the platform rather than from isolated tables. Identity management led to the `user`, `account`, `session`, `verification`, `role`, and `user_role` entities. Listing publication required location, photo, amenity, house-rule, and availability tables. The booking flow introduced bookings, fees, payment transactions, payouts, cancellation policies, and reviews. Engagement features such as messaging, wishlists, notifications, and referrals were modeled as separate but related parts of the same system. This structure supported third normal form because repeated concepts were placed into their own entities, many-to-many relationships were handled through bridge tables, and non-key attributes generally depended on the key of their own table rather than on other descriptive fields.

In the second phase, the conceptual model was translated into a working PostgreSQL 18.3 implementation. Docker and Docker Compose were used to run PostgreSQL and pgAdmin in a reproducible environment, which kept the project portable and avoided depending on a local database installation. The schema was implemented in dependency order, using PostgreSQL features such as UUID primary keys, foreign keys, `UNIQUE` constraints, `CHECK` constraints, JSONB columns, arrays, timestamps, ISO currency codes, and supporting indexes. These choices helped turn the academic ER model into a practical relational system that could be populated and tested.

The seeding strategy was an important part of making the database usable. A Python script managed through UV inserted deterministic sample data into the running PostgreSQL database with Faker and psycopg. The script used a fixed seed and combined German and Colombian Spanish locales so that names, locations, currencies, and listing details felt more varied and realistic. The final dataset populated every table with at least the required minimum number of rows, producing more than 560 rows across the schema. After seeding, a static SQL snapshot was exported with `pg_dump` so that the populated state could be reused without rebuilding the data generation process each time.

Functional validation was done through a catalog of relational test queries. These were not limited to simple row-count checks. Instead, they represented realistic platform questions: active sessions, linked sign-in methods, role assignments, location paths, amenity usage, listing search results, host calendar blocks, booking summaries, payment timelines, payout ledgers, conversation activity, wishlist contents, verified reviews, and notifications. Additional analytical queries combined financial, geographic, and reputation data to show that the normalized schema could support reporting as well as operational workflows.

Looking back, the conceptual decisions from phase 1 held up well during implementation. The normalized design made the SQL schema easier to reason about because each table had a clear responsibility. The separation of payments and payouts, the use of bridge tables, and the normalized location tree all made the data model more flexible than a flatter design would have been. At the same time, the project also showed the cost of strong normalization: useful queries often required several joins, and some workflows became more complex to seed because related data had to be inserted in the correct order. This was a reasonable tradeoff for the project because correctness, clarity, and relational integrity were more important than minimizing query length.

The main engineering takeaway from the full lifecycle is that careful conceptual design reduces uncertainty later. Phase 2 did not require major redesign because phase 1 had already defined the business rules, relationships, and constraints with enough precision. The harder work was not creating tables, but making the database feel realistic through seeded data and proving its usefulness through meaningful queries. Overall, the project demonstrated how an academic ER model can become a functioning PostgreSQL datamart when assumptions, normalization, implementation, and validation are treated as connected parts of the same development process.
